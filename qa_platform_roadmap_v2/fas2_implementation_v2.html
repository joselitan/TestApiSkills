⚡ Fas 2 — Prestanda och realtid

Caching, WebSocket och kryptering — utan onödig infrastruktur

Krav: Fas 1 klar  ·  Svårighet: ⭐⭐⭐ Medel  ·  Uppskattad tid: 2–3 veckor

📋 Vad handlar den här fasen om?

Nu när säkerhetsgrunden är på plats kan vi göra plattformen snabbare och mer interaktiv. Den gamla v2-planen föreslog Redis och Celery — det är onödig komplexitet för ett utbildningsprojekt. Vi uppnår samma mål med enklare verktyg.

⚠️ Varför inte Redis och Celery?

Redis kräver en separat server-process. Celery kräver Redis plus en worker-process. Det är tre processer att hålla igång istället för en. flask-caching med SimpleCache ger oss caching utan extra infrastruktur. threading hanterar bakgrundsjobb. Resultatet är detsamma — komplexiteten är lägre.

📦 Nya paket att installera

pip install flask-caching flask-socketio

cryptography finns redan i requirements.txt.
Lägg till flask-caching>=2.1.0 och flask-socketio>=5.3.0 i requirements.txt.

💾 Steg 1 — Enkel caching

Vad är problemet nu?

Dashboard-endpointsen i dashboard/backend/app.py kör samma SQL-frågor varje gång någon laddar dashboarden. Med caching sparar vi resultatet i minnet i 5 minuter och svarar direkt utan att fråga databasen.

Ny fil: dashboard/backend/cache_config.py

from flask_caching import Cache

# SimpleCache sparar allt i serverns minne — ingen extern service behövs
cache = Cache(config={
    "CACHE_TYPE": "SimpleCache",
    "CACHE_DEFAULT_TIMEOUT": 300 # 5 minuter
})

Ändra i dashboard/backend/app.py

from cache_config import cache

# Initialisera cachen med appen
cache.init_app(app)

# Lägg till @cache.cached på tunga endpoints
@app.route("/api/dashboard/summary")
@cache.cached(timeout=300, key_prefix="dashboard_summary")
def get_dashboard_summary():
    # ... befintlig SQL-kod — rör ingenting ...

@app.route("/api/dashboard/test-types")
@cache.cached(timeout=300, key_prefix="test_types")
def get_test_types_breakdown():
    ...

# När nya testresultat kommer in — rensa cachen
@app.route("/api/test-runs", methods=["POST"])
def add_test_run():
    # ... befintlig logik ...
    cache.clear() # Tvinga fram ny data nästa gång
    return jsonify({"success": True, "run_id": run_id})

Hur testar vi det?

def test_dashboard_summary_is_cached(client):
    """Andra anropet ska vara snabbare — cachen fungerar"""
    import time
    t1 = time.time(); client.get("/api/dashboard/summary"); t1 = time.time() - t1
    t2 = time.time(); client.get("/api/dashboard/summary"); t2 = time.time() - t2
    # Cachat svar ska vara snabbare
    assert t2 < t1

📡 Steg 2 — WebSocket för live test-resultat

Vad är problemet nu?

Just nu uppdateras dashboard-sidan bara om man manuellt laddar om den. conftest.py skickar redan resultat via HTTP POST under testkörningen — men dashboard-sidan vet inte om det. Med WebSocket pushas uppdateringar direkt till webbläsaren i realtid.

Ändra i dashboard/backend/app.py

from flask_socketio import SocketIO, emit

socketio = SocketIO(app, cors_allowed_origins="*")

# Befintlig POST /api/test-runs — lägg till emit i slutet
@app.route("/api/test-runs", methods=["POST"])
def add_test_run():
    # ... befintlig logik ...
    cache.clear()
    
    # Skicka live-uppdatering till alla anslutna webbläsare
    socketio.emit("test_result", {
        "passed": data.get("passed_tests"),
        "failed": data.get("failed_tests"),
        "test_type": data.get("test_type")
    })
    return jsonify({"success": True})

# Starta med socketio istället för app.run
if __name__ == "__main__":
    init_db()
    socketio.run(app, debug=True, port=6001)

Lägg till i dashboard/frontend/index.html

<!-- Lägg till i <head> -->
<script src="https://cdn.socket.io/4.7.2/socket.io.min.js"></script>

<!-- Lägg till i <script> -->
const socket = io("http://localhost:6001");

socket.on("test_result", function(data) {
    // Uppdatera siffrorna på dashboarden direkt
    document.getElementById("passed-count").textContent = data.passed;
    document.getElementById("failed-count").textContent = data.failed;
    console.log("Live uppdatering:", data);
});

Effekten

Kör pytest tests/api/ i en terminal och titta på dashboard-sidan i webbläsaren. Siffrorna uppdateras i realtid för varje test som slutförs — utan att sidan behöver laddas om.

🔐 Steg 3 — Kryptering av e-postadresser

Vad är problemet nu?

E-postadresser lagras i klartext i guestbook.db. Om databasen läcker kan alla e-postadresser läsas direkt. Vi krypterar dem med Fernet från cryptography-paketet som redan är installerat.

⚠️ Viktigt att tänka på

Krypteringsnyckeln måste sparas säkert — aldrig i koden eller i Git-repot. Den ska ligga i en miljövariabel eller en separat nyckel-fil utanför repot. Vi löser det med .env-fil och python-dotenv.

Ny fil: src/encryption.py

import os
from cryptography.fernet import Fernet

def get_cipher():
    """Hämta krypteringsobjektet från miljövariabeln ENCRYPTION_KEY."""
    key = os.getenv("ENCRYPTION_KEY")
    if not key:
        raise ValueError("ENCRYPTION_KEY saknas i miljövariabler")
    return Fernet(key.encode())

def encrypt_email(email: str) -> str:
    """Kryptera en e-postadress. Returnerar krypterad sträng."""
    return get_cipher().encrypt(email.encode()).decode()

def decrypt_email(encrypted: str) -> str:
    """Dekryptera en e-postadress. Returnerar klartext."""
    return get_cipher().decrypt(encrypted.encode()).decode()

# Hjälpfunktion för att generera en ny nyckel
# Kör EN gång: python -c "from encryption import generate_key; generate_key()"
def generate_key():
    key = Fernet.generate_key().decode()
    print(f"Lägg detta i din .env-fil: ENCRYPTION_KEY={key}")

Ändra i blueprints/v1/guestbook.py

from encryption import encrypt_email, decrypt_email

# Vid CREATE — kryptera e-post innan lagring
def create_entry():
    # ... validering ...
    encrypted = encrypt_email(email)
    cursor.execute(
        "INSERT INTO guestbook (name, email, comment) VALUES (?, ?, ?)",
        (name, encrypted, comment)
    )

# Vid GET — dekryptera e-post i svaret
def get_all_entries():
    # ... SQL-fråga ...
    result = []
    for entry in entries:
        row = dict(entry)
        row["email"] = decrypt_email(row["email"]) # Visa klartext i API-svaret
        result.append(row)
    return jsonify({"data": result, "meta": {...}})

💡 Migrering av befintlig data

Befintliga poster i databasen har okrypterade e-postadresser. Innan kryptering aktiveras behöver vi köra ett migreringsscript som krypterar alla befintliga rader. Det skriver vi när vi implementerar detta steg.

🔄 Steg 4 — Bakgrundsjobb för Excel-import

Vad är problemet nu?

/api/v1/guestbook/import blockerar HTTP-requesten medan Excel-filen bearbetas. En stor fil kan ta flera sekunder. Vi kör importen i en bakgrunds-tråd och returnerar ett jobb-ID direkt. Ingen Celery eller Redis — bara Pythons inbyggda threading.

Ändra i blueprints/v1/guestbook.py

import threading
import uuid

# Enkel in-memory jobbstatus
import_jobs = {}

def _run_import(job_id, file_bytes):
    """Körs i bakgrunden — inte i HTTP-requesten."""
    try:
        import_jobs[job_id] = {"status": "running", "imported": 0}
        # ... befintlig import-logik ...
        import_jobs[job_id] = {"status": "done", "imported": count}
    except Exception as e:
        import_jobs[job_id] = {"status": "error", "message": str(e)}

@bp.route("/guestbook/import", methods=["POST"])
@token_required
def import_excel():
    # ... validering av filen ...
    file_bytes = file.read() # Läs filen direkt
    job_id = str(uuid.uuid4())
    thread = threading.Thread(target=_run_import, args=(job_id, file_bytes))
    thread.start()
    return jsonify({"job_id": job_id, "status": "queued"}), 202

@bp.route("/guestbook/import/<job_id>", methods=["GET"])
@token_required
def get_import_status(job_id):
    job = import_jobs.get(job_id)
    if not job:
        return jsonify({"message": "Jobb hittades inte"}), 404
    return jsonify(job)
